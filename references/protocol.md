## 1. 任务路由表

| 类型 | 判定标准 | 执行者 |
|---|---|---|
| T0 微编辑 | 单文件、位置已知、改动 ≤10 行 | Claude 直接用 Edit 工具改 |
| T1 探索/定位 | 需要读 ≥3 个文件，或代码结构未知 | codex（只读） |
| T2 实现/重构 | 跨文件改动，或单文件 >10 行 | codex（可写） |
| T3 测试修错循环 | 跑测试→修→再跑直至通过 | codex（可写，续接 T2 的 thread） |

边界与升级规则：

- 体量拿不准时，默认按更大的类型处理。
- T0 进行中发现超出边界 → 立即停手，把已知信息写成任务书升级为 T2。
- T1 例外：架构决策性质的探索（方案选型、依赖梳理）不降推理档，用默认档。
- 活跃 thread 涉及的路径范围内，Claude 不做 T0 微编辑；确有必要改动，必须在下一次 codex-reply 中告知改动点。
- 委托有任务书、启动和验收开销；位置已知的微编辑保留给 Claude。未知结构、跨文件修改、测试循环或长任务优先委托。

## 2. 调用参数矩阵与执行通道（每次调用显式传参，不改全局 config.toml）

| 类型 | sandbox | approval-policy | config 覆盖 | cwd |
|---|---|---|---|---|
| T1（常规定位） | `read-only` | `never` | `{"model_reasoning_effort": "low"}` | 项目根，显式传 |
| T1（架构决策类） | `read-only` | `never` | 无 | 项目根，显式传 |
| T2 机械类（成文、格式转换、模板化改动） | `workspace-write` | `never` | `{"model_reasoning_effort": "low"}` | 项目根，显式传 |
| T2 逻辑类（重构、算法、多文件实现）/ T3 | `workspace-write` | `never` | 无 | 项目根，显式传 |

推理档判据：产出可以从任务书机械推导（照说明成文、照模板改动）→ low；需要 codex 自己做设计决策 → 默认档。
**优先级覆盖规则：质量敏感为最高优先级**——命中质量优先模式的任务一律禁用 low 档（即使产出机械可推导），是否 one-shot 另行判定（机械可推导的质量敏感任务可以"N 路 one-shot 并行 + 评审"，档位用默认档）。

### 执行通道：同步 MCP vs 后台 exec

- 预计 <3 分钟的轮次（追问、小修正、验收核对）→ 同步 MCP（`codex` / `codex-reply`）。
- 预计 ≥3 分钟的长轮、或多个可并行的独立任务 → 后台 exec，经 `scripts/launch.sh` 发射。脚本校验参数和任务书、锁定 slug、归档上一轮、记录内容与权限基线、从 stdin 传递任务书、用 `--strict-config` 校验覆盖项、超时后终止进程组，并原子写入 `<slug>.status`。**超时轮的工作区状态视为未知，验收前必须核查改动，禁止直接续轮。**
- **完成判据以 `<slug>.status` 为权威**（失败轮可能根本没有 `.last.md`）。Monitor 兜底监视 `.status` 出现而非 `.last.md`。Claude 只读 `.last.md` 与 `.status`；**严禁读 events.jsonl 全文**（只用 grep 提取字段）。
- 续接凭据：launch.sh 从 JSONL 的 session/thread 字段提取 UUID，写入 `<slug>.session`，并记入 ACTIVE.md（exec 记 session id，MCP 记 threadId，注明通道）。不要用“任意首个 UUID”代替结构化提取。
- 续接：launch.sh 第 6 参传 resume_session_id。脚本只接受能由当前项目 `.session` 凭证证明的 UUID，并重传 sandbox 与 approval 覆盖；无法证明项目根一致时拒绝并冷启动。若凭证对应的最新 status 是 timeout，先人工审查工作区，再对本次命令显式设置 `CODEX_AGENT_TIMEOUT_REVIEWED=1`；没有该确认时脚本拒绝 resume。exec 与 MCP 会话不互通，一个工作流全程只用一种通道。
- 并行多个后台 exec 必须范围隔离（各任务书「涉及路径」不重叠）；**同一 git 工作区同时最多一个可写（T2/T3）任务**——并行可写需独立 worktree/分支，只读任务不限。
- 唤醒兜底（**硬性要求，实测已失灵两次**）：发起后台 exec 的同时**必须**布防独立定时唤醒（Monitor until 循环监视 `<slug>.status` 出现，带超时），不得仅依赖后台完成通知。双通知无害；单通道停摆实测导致 25 与 40 分钟两次空等。"为避免双通知而不布兜底"是被禁止的判断。
- 非 one-shot 的 exec 任务必须把第 5 节汇报协议全文并入任务书（exec 无 developer-instructions 参数，漏并入 = codex 自由格式汇报）。

## 3. 前置检查与安全护栏（工作流启动前依次执行）

0. **定项目根（一切状态锚点的前提，实战踩过的坑）**：项目根 = **本次任务目标文件所在项目的根**，判定顺序：① 任务涉及路径的 git 仓库根（`git -C <任务路径> rev-parse --show-toplevel`）；② 非 git 则取包含全部任务范围的最上层项目目录。**绝不是会话的 cwd**——一个会话操作多个项目时，cwd 只有碰巧才对。`.codex-agent/`（ACTIVE.md、日志、地图、marker、status）一律建在按此判定的项目根下，各项目各一套互不混用。任务范围横跨两个项目根 → 拆成每项目一个工作流。嵌套仓库取最内层包含任务范围的根。CLAUDE.md 恢复锚点同理：检查的是当前要动的项目的 ACTIVE.md，不只是 cwd 的。
1. git 检查：项目非 git 仓库 → 先征得用户同意后 `git init` 并做初始 commit；用户拒绝则降级——codex 汇报必须列完整改动文件清单、Claude 逐一抽查，并明确告知用户此模式无回滚能力。
2. 检查点：每轮 T2/T3 开始前确认存在可回滚基线。**只允许 commit/stash 本工作流自己产生的改动**；发现用户或其他工作流的未提交改动 → 停下询问用户，禁止自动 commit/stash 他人内容。做法：记录基线 commit（`git rev-parse HEAD`），每轮验收用相对基线的 diff，而非要求全局 clean。
3. 禁止事项固定项：破坏性 git 操作（reset --hard、push --force、改写历史）、删除非任务范围文件、修改全局配置。
4. 信任前提：新项目首次使用前确认 `~/.codex/config.toml` 中该目录为 `trusted`。
5. 测试工具链预探测（B7 教训）：含测试的任务发起前，先用一条本地命令探测 runner 可用性（约 5 秒）；不可用或不明时，备好兜底解释器并把**绝对路径写进首轮任务书**。**沙箱边界注意**：兜底 venv 必须预先建好、任务中只执行不安装；建在系统临时目录下（workspace-write 沙箱默认可写 $TMPDIR，B7 实证）或显式加入最小 writable root——禁止用扩大沙箱范围隐式解决 runner 问题。
6. 平台适配：**macOS** 全量实测验证（注意系统 bash 3.2 的多字节变量解析坑，脚本已规避）；**Linux** 兼容（脚本依赖 Bash 而非纯 POSIX + landlock 沙箱），首次使用跑一次 T1 冒烟即可；**Windows：WSL 优先**（WSL 内等同 Linux 路径）。原生 Windows：需 Git Bash 跑两个脚本、verify.sh 已内置 python3/python 命名探测；**codex 沙箱在原生 Windows 为实验性——沙箱保障不等价时改传 `-c approval_policy="on-request"`（launch.sh 需相应调整）并告知用户**；任务书与 writable_roots 中的路径注意分隔符。

```

（一句话说清要达成什么）

涉及路径：<明确列出>
禁止改动：破坏性 git 操作；删除非任务范围文件；修改全局配置；<任务特定项>

## 已知上下文
（Claude 已掌握的信息直接贴入：目录结构摘要、关键代码片段、上一轮结论。
 这是让 codex 跳过探索阶段的关键提速点。
 若存在 <项目根>/.codex-agent/PROJECT-MAP.md，第一条就写：
 "先读 PROJECT-MAP.md 获取项目结构，只对与本任务相关的部分做验证性探索"。
 若存在历史日志文件，给出路径让 codex 自行阅读，不粘贴内容。）

## 执行效率要求
探索命令尽量合并为单条复合命令（for 循环批处理）——你每执行
一条命令就是一次约 18 秒的模型往返，循环次数直接决定耗时。
若发现 PROJECT-MAP.md 与实际不符，顺手修正它（仅 workspace-write 轮）。
（机械成文类任务加 one-shot 条款：零探索零自验，直接产出目标文件；
 验证由指挥方全权负责，完成标准可标注"由指挥方验证"。）

## 日志文件
本工作流日志：<项目根>/.codex-agent/<工作流slug>.md
每轮结束将完整汇报追加写入该文件（格式见汇报协议）。

## 完成标准
（可逐条验证的条目，codex 汇报时逐条对照）

## 体量与熔断
本轮任务体量控制在约 10 分钟内可完成；
（T3 专用）测试修错尝试 3 次仍未通过 → 停止并汇报当前状态。
```

拆轮规则：MCP 调用同步阻塞，预估超约 10 分钟的任务必须拆成多轮，通过同一 thread 逐轮下发。

## 5. 汇报协议（MCP 经 developer-instructions 注入；exec 并入任务书；全文固定）

```
每轮结束时，你必须以下列五段格式汇报，标题一字不差：

## 结果
改动摘要，一律用 文件:行号 引用；探索类任务给结论和证据位置

## 过程
关键步骤，最多 5 条

## 遇到的问题

## 解决方式

## 遗留风险与建议
无则写"无"

约束：
- 不要向汇报中粘贴大段代码（>10 行），只给 file:line 引用。
- 完成标准逐条标注 ✅/❌。每个 ✅ 必须在同一行写明结论、执行的命令原文、exit code 与输出摘要；没有逐项证据的结论不要标 ✅。禁止把多个 ✅ 与一条汇总证据拆开书写。
- 最终消息给精简版（每段 ≤3 条）；同时把完整版汇报（五段全文 +
  附录：关键命令完整输出、diff 摘要）追加写入任务书指定的
  日志文件，本轮标题为 `# Round N`（threadId 由指挥方验收时补记——
  codex 无法看到自己的 threadId，不要要求它自标）。
```

- T1 只读沙箱无法写文件：注入时将"写入日志文件"约束替换为"完整版汇报直接放在最终消息中，由指挥方落盘"。
- **one-shot 任务免五段汇报**（B8 修订）：产物即汇报——codex 最终消息一行确认即可，验收判据全部由 verify.sh + 指挥方内容把关承担。
- 协议容错：汇报格式不符、证据缺失或漏写日志文件时，用一次 codex-reply 纠正补交，不重开 thread；纠正后仍不符按"无实质进展"计入熔断。
- **修正轮的边界（与质量优先模式的关系）**：协议合规补交与客观缺陷修复（格式、证据、❌ 项、bug）允许一次原会话串行修正；**主观质量打磨**（表述、结构、深度不满意）禁止串行迭代——用加并行臂解决。两者的判据：有明确判错标准的是缺陷，凭偏好判优劣的是打磨。

## 6. Thread 生命周期与异常处理

- **每个工作流只使用一个会话；一个会话可被多个工作流串行复用**（暖会话）。首轮用 `codex` 工具，之后一律 `codex-reply` + `threadId`。日志、轮次编号、归档文件一律按**当前工作流的 slug** 归属，与会话来源无关；ACTIVE.md 行内注明"复用自 <来源 slug>"。
- sandbox 是 thread 级配置：read-only 的 T1 thread **无法**续接 workspace-write 的 T2 轮。探索后确定要实现的任务，直接开 workspace-write thread，任务书内含"先探索后实现"一轮完成；仅当探索结论需 Claude 决策后才实现时，才拆两个 thread（结论经日志传递）。T2→T3 同为 workspace-write，可同 thread 续接。
- Claude 每次收到汇报后在可见回复中记录 threadId。
- 新的独立任务开新 thread。**暖会话例外**：同项目同域新任务，无冲突风险时优先续用暖会话（MCP 用 codex-reply；exec 用 resume）——探索成本归零（B4 实测零探索命令；会话磁盘持久化，跨小时级间隔有效）。复用时在 ACTIVE.md 标注来源 slug。
  **resume 硬性检查**：resume 继承原会话 cwd 且不支持 `-C`；sandbox 用 config 覆盖。launch.sh 用当前项目内的 `.session` 凭证校验来源，无法证明同根就拒绝。推理档、approval 等 config 每次重新显式传，不假设继承。复用超过 3–4 轮或跨天后冷启动换新，避免历史上下文持续膨胀。
- 熔断：同一 thread 连续 2 轮无实质进展 → 放弃，重新分析、换策略、开新 thread。
- 冷启动：任务书「已知上下文」给日志文件路径让 codex 自行阅读，不粘贴历史内容。
- threadId 失效降级：codex-reply 报错 → 不重试，直接冷启动开新 thread。
- 同一 thread 内不重复传递上一轮内容——codex-reply 已保有全部历史。

## 7. 验证闭环（Claude 侧）

1. codex 按协议汇报（含原始证据）。
2. `git diff --stat` 核对改动范围（非 git 降级模式：核对汇报中的改动文件清单）。
3. 后台 exec 通道验收用 `scripts/verify.sh <项目根> <slug> [oneshot|full] [允许路径正则]`。非零退出码即不通过；workspace-write 轮缺少允许路径正则也必须失败。脚本检查终态、相对发射前内容与权限快照的新增/修改/删除、允许路径、五个固定标题、❌、至少一个 ✅，并要求每个 ✅ 同行包含命令、exit code 与输出证据。正则按完整相对路径匹配。
4. 只抽查关键 hunk，不重读整个文件；每个 ✅ 必须有原始证据（命令 + exit code + 输出尾行），只有结论视为 ❌。
5. 最终验收：Claude 自己执行一次测试/验证命令，不全信汇报。例外——纯文档类任务免复跑，改为抽查成品 + 核对改动清单。
6. 全 ✅ 且最终验收通过才收尾；出现 ❌ 或遗留风险 → codex-reply 下修正指令。
7. **面向用户的收尾汇报（硬性）**：验收通过后，大脑必须在对话中向用户交付结果本体——① 交付物清单与各自的关键内容摘要（几句话说清里面是什么，不是只给路径）；② 探索/审校/分析类任务的结论、发现、数字**原文进对话**（这类任务用户要的就是内容本身）；③ 验收结果与遗留风险。文件是持久层（供恢复与审计），对话是交付层——"内容已写入文件"不构成对用户的交付。token 节省的对象是过程噪音（codex 的探索输出、完整事件流），永远不是用户要的结果。

## 8. 汇报落盘与恢复

日志文件：`<项目根>/.codex-agent/<工作流slug>.md`（跨会话持久；git 仓库中加入 .gitignore）。

- 写入分工：T2/T3 由 codex 自行追加；T1 由 Claude 代写；文件头（任务总目标、threadId、任务书原文）由 Claude 在工作流开始时写入。
- Claude 读取规则——仅三种情况读日志：① 压缩后找回历史/threadId；② 新会话恢复；③ 需核对某轮完整细节。正常轮次不得重读。

状态清单：`<项目根>/.codex-agent/ACTIVE.md`，每行一个工作流：

```
- <slug> | 状态: active/blocked/done | threadId: xxx | 轮次: N | 下一步: <一句话>
```

- Claude 在每轮验收后、发起下一轮之前更新对应行；完结改 done，done 条目下次更新时移除。
- **并发锁（多会话防互踩）**：更新 ACTIVE.md 前先 `mkdir <项目根>/.codex-agent/.lock`（原子操作）抢锁并在锁内写 owner 文件（pid/host/时间），失败则等 2–5 秒重试；更新完删 owner 后 `rmdir` 释放。**强拆条件**：锁超过 60 秒**且** owner 进程已不存活（本机 `kill -0 <pid>` 验证）；owner 无法验证（跨主机/无 owner 文件）时不得自动强拆，提示用户人工处置。
- **slug 预留必须原子**：「持锁查 ACTIVE.md → 写入占位行 → 释放锁」一个事务内完成，然后才允许发射；launch.sh 的运行锁在发射层再拦一道——同 slug 并发发射直接拒绝，绝不归档活跃任务产物。
- 轻量簿记：预计 ≤2 轮的工作流免文件头预写和逐轮维护——结束一次性写简化日志 + ACTIVE.md 一行 done。第 3 轮起转全量。

恢复流程（压缩 / /clear / 会话切换通用）：

1. 锚点在全局 CLAUDE.md："开始代码工作前，若项目根存在 .codex-agent/ACTIVE.md，先读取并恢复未完结工作流"。
2. 读 ACTIVE.md → 定位未完结工作流 → 读对应日志的文件头与最后一轮汇报。
3. 先试 codex-reply + 记录的 threadId；失败则冷启动（见第 6 节）。
4. 轮次边界纪律：状态更新先于下一轮下发，任意时刻被重置最多丢失当前一轮。

多终端 / 多项目并发：

- 多项目：skill 全局唯一，状态严格项目本地化，cwd 每次显式传，项目间互不干扰。
- 多终端同项目：**MCP thread 存活于各终端自己的 mcp-server 进程，不跨终端**；**exec session 持久化在磁盘，技术上可跨终端 resume**——但管理约束不变：工作流归属创建它的会话，接管他人 active 工作流须经用户确认（exec 可直接 resume 其 session id，MCP 走冷启动）。
- ACTIVE.md 更新一律行级 Edit + 并发锁，禁止整文件重写（初次创建除外）。
- slug 唯一性：开新工作流前查 ACTIVE.md，被 active 占用则换名。
- 范围隔离：多会话并行委托的「涉及路径」不得重叠；git 检查点发现他人未提交改动，不得 stash，提醒用户处理。

项目结构地图：`<项目根>/.codex-agent/PROJECT-MAP.md`——目录职责索引 + 关键文件位置 + 各部分现状，供任务书引用免除重复探索（实测探索占 codex 循环 2/3 以上）。维护纪律：

- 首次委托时由当次探索结果生成；workspace-write 轮 codex 发现偏差顺手修正，read-only 轮由 Claude 依汇报修正；只记稳定结构。
- **新鲜度戳（防腐化）**：地图头部维护「校订: <日期> by <工作流slug>」，任何修正同步更新戳。发起 one-shot 前检查：若项目内容明显新于校订戳（`ls -t` 首屏多为戳后文件），先跑一次 T1 校订地图再 one-shot——one-shot 零探索，最依赖地图准确，喂错地图 = 产出错误事实。
