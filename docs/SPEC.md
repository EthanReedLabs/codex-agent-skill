# Codex 委托执行结构设计（codex-agent）

日期：2026-07-16
状态：已经用户确认（v2，含短板补齐与收益评估）

## 背景与目标

当前在 Claude Code 中通过 codex MCP 做代码修改，存在两个问题：单次调用慢（codex 从零探索、审批往返、推理档位偏高）、结果回传无固定结构（Claude 解析汇报费 token）。

目标：建立一套「Claude 指挥、codex 执行」的分工结构——

1. 省 Claude 上下文 token：读密集、写密集的任务全部委托 codex，代码内容尽量不进 Claude 上下文。
2. 降低延迟：消除 codex 的重复探索和审批往返，探索类任务降推理档。
3. 结构化回传：codex 必须按固定协议汇报结果、过程、遇到的问题、解决方式，供 Claude 分析后下达下一轮指令。
4. 可信与可恢复：汇报须附可复核证据；工作流状态落盘，可跨压缩、跨会话恢复；改动可回滚。

## 1. 任务路由表

| 类型 | 判定标准 | 执行者 |
|---|---|---|
| T0 微编辑 | 单文件、位置已知、改动 ≤10 行 | Claude 直接用 Edit 工具改 |
| T1 探索/定位 | 需要读 ≥3 个文件，或代码结构未知 | codex（只读） |
| T2 实现/重构 | 跨文件改动，或单文件 >10 行 | codex（可写） |
| T3 测试修错循环 | 跑测试→修→再跑直至通过 | codex（可写，续接 T2 的 thread） |

T0 不委托的理由：任务书 + 汇报 + 验证的往返开销超过 Claude 直接编辑，委托反而更慢更费 token。

**边界与升级规则：**

- 体量拿不准时，默认按更大的类型处理（宁可委托，不污染 Claude 上下文）。
- T0 进行中发现超出边界（改动变大、牵连其他文件）→ 立即停手，把已知信息写成任务书升级为 T2。
- T1 例外：结论具有架构决策性质的探索（方案选型、依赖关系梳理，而非简单定位）不降推理档，用默认档执行。
- 活跃 thread 涉及的路径范围内，Claude 不做 T0 微编辑（防止 codex 基于过期文件内容修改）；确有必要改动，必须在下一次 `codex-reply` 中告知改动点。

## 2. 调用参数矩阵

每次调用时显式传参，不修改全局 `~/.codex/config.toml`。

| 类型 | sandbox | approval-policy | config 覆盖 | cwd |
|---|---|---|---|---|
| T1（常规定位） | `read-only` | `never` | `{"model_reasoning_effort": "low"}` | 项目根，显式传 |
| T1（架构决策类） | `read-only` | `never` | 无（默认档） | 项目根，显式传 |
| T2 机械类（成文、格式转换、模板化改动） | `workspace-write` | `never` | `{"model_reasoning_effort": "low"}` | 项目根，显式传 |
| T2 逻辑类（重构、算法、多文件实现）/ T3 | `workspace-write` | `never` | 无（默认档） | 项目根，显式传 |

推理档判据：产出可从任务书机械推导 → low；需要 codex 自己做设计决策 → 默认档。

**执行通道（2026-07-16 提速修订）**：预计 <3 分钟的轮次走同步 MCP；≥3 分钟的长轮或可并行的独立任务走后台 `codex exec`（Bash run_in_background）——`-C <项目根> -s <sandbox> --skip-git-repo-check --json -o <slug>.last.md`，汇报协议并入 prompt（exec 无 developer-instructions 参数）。完成后只读 `.last.md`，session id 从 events.jsonl 用 grep 提取（严禁读全文），续接用 `codex exec resume <SESSION_ID> --skip-git-repo-check`（该旗标 resume 时也必须带，实测缺省会因信任检查报错）。exec 与 MCP 会话不互通，一个工作流只用一种通道；并行 exec 必须范围隔离。此举把 codex 执行时间从阻塞变为并发，是最大的省时杠杆。

设计依据：

- T1 常规探索不需要深推理，低档位延迟降幅最大；架构决策类结论是下游一切的地基，不省这个钱。
- T2/T3 用 `approval-policy: never` 消除审批往返；质量档位不降。
- 模型名不硬编码，跟随 codex 默认配置，将来换模型无需改协议。

## 3. 前置检查与安全护栏

`approval-policy: never` + 可写沙箱意味着 codex 可以无审批执行工作区内的任意命令，必须有回滚保障。工作流启动前，Claude 依次检查：

1. **git 检查**：项目非 git 仓库 → 先征得用户同意后 `git init` 并做初始 commit；用户拒绝则降级——codex 汇报中必须列出完整改动文件清单，Claude 逐一抽查（明确告知用户此模式无回滚能力）。
2. **检查点**：每轮 T2/T3 开始前工作区必须处于干净 commit 点（未提交改动先 commit 或 stash），改坏可整轮回滚。
3. **禁止事项固定项**：任务书「禁止改动」一栏固定包含——破坏性 git 操作（`reset --hard`、`push --force`、改写历史）、删除非任务范围文件、修改全局配置。
4. **信任前提**：新项目首次使用前确认 `~/.codex/config.toml` 中该目录为 `trusted`，避免沙箱行为不一致。

## 4. 任务书模板（codex 首轮 prompt 的固定结构）

```markdown
## 目标
（一句话说清要达成什么）

## 范围
涉及路径：<明确列出>
禁止改动：破坏性 git 操作；删除非任务范围文件；修改全局配置；<任务特定项>

## 已知上下文
（Claude 已掌握的信息直接贴入：目录结构摘要、关键代码片段、
 上一轮结论。这是让 codex 跳过探索阶段的关键提速点。
 若存在历史日志文件，给出路径让 codex 自行阅读，不粘贴内容。）

## 日志文件
本工作流日志：<项目根>/.codex-agent/<工作流slug>.md
每轮结束将完整汇报追加写入该文件（格式见汇报协议）。

## 完成标准
（可逐条验证的条目，codex 汇报时逐条对照）

## 体量与熔断
本轮任务体量控制在约 10 分钟内可完成；
（T3 专用）测试修错尝试 3 次仍未通过 → 停止并汇报当前状态。
```

**拆轮规则**：MCP 调用是同步阻塞的，预估超过约 10 分钟的任务必须由 Claude 拆成多轮，通过同一 thread 逐轮下发。每轮汇报同时成为进度检查点，也规避客户端超时导致的半途丢失。

## 5. 汇报协议（通过 `developer-instructions` 参数注入，全文固定）

```markdown
每轮结束时，你必须以下列五段格式汇报，标题一字不差：

## 结果
改动摘要，一律用 文件:行号 引用；探索类任务给结论和证据位置

## 过程
关键步骤，最多 5 条

## 遇到的问题

## 解决方式

## 遗留风险与建议
无则写"无"

约束：
- 不要向汇报中粘贴大段代码（>10 行），只给 file:line 引用。
- 完成标准逐条标注 ✅/❌，每个 ✅ 必须附可复核的原始证据：
  执行的命令原文、exit code、输出末尾 5 行。禁止只写结论。
- 最终消息给精简版（每段 ≤3 条）；同时把完整版汇报（五段全文 +
  附录：关键命令完整输出、diff 摘要）追加写入任务书指定的
  日志文件，本轮标题为 `# Round N (threadId: xxx)`。
```

（T1 只读沙箱无法写文件，其汇报由 Claude 收到后写入同一日志文件。）

**协议容错**：汇报格式不符、证据缺失或漏写日志文件时，Claude 用一次 `codex-reply` 纠正补交，不重开 thread；纠正后仍不符按"无实质进展"计入熔断。

## 6. Thread 生命周期与异常处理

- 一个工作流 = 一个 thread。首轮用 `codex` 工具，之后所有追问、修正、测试循环一律 `codex-reply` + `threadId`。
- Claude 每次收到汇报后在可见回复中记录 threadId，防止上下文压缩后丢失。
- 新的独立任务开新 thread，不复用旧 thread（避免上下文污染）。
- 熔断规则：同一 thread 连续 2 轮无实质进展 → 放弃该 thread，Claude 重新分析、换策略、开新 thread。
- 冷启动：开新 thread（熔断重开或跨会话恢复）时，任务书「已知上下文」给日志文件路径让 codex 自行阅读，Claude 不粘贴历史内容。
- **threadId 失效降级**：`codex-reply` 报错（thread 不存在，如 MCP server 重启后）→ 不重试，直接走冷启动流程开新 thread。这是落盘机制"跨会话恢复"承诺的兑现路径。
- 同一 thread 内**不**重复传递上一轮内容——codex-reply 续接的会话已保有全部历史，重复传递是纯浪费。

## 7. 验证闭环（Claude 侧）

1. codex 按协议汇报（含原始证据）。
2. Claude 跑 `git diff --stat` 核对改动范围是否越界（非 git 降级模式：核对汇报中的改动文件清单）。
3. 只抽查关键 hunk，不重读整个文件。
4. 核对每个 ✅ 的证据是否为原始输出（命令 + exit code + 输出尾行），只有结论没有证据视为 ❌。
5. **最终验收**：工作流收尾时 Claude 自己执行一次测试/验证命令（一条 Bash，成本极低），不全信汇报。例外——纯文档类任务（不改代码、不影响运行时行为）免复跑，验收改为抽查成品 + 核对改动文件清单。
6. 完成标准全 ✅ 且最终验收通过才收尾；出现 ❌ 或遗留风险 → `codex-reply` 下修正指令。

## 8. 汇报落盘与恢复机制

每个工作流对应一个日志文件：`<项目根>/.codex-agent/<工作流slug>.md`（项目本地、跨会话持久；git 仓库中加入 .gitignore）。

**写入分工：**

- T2/T3：codex 在每轮结束时自行追加完整汇报（写文件指令包含在汇报协议中），Claude 零 token 开销。
- T1：只读沙箱无法写文件，由 Claude 收到汇报后写入（T1 汇报本身很短）。
- 文件头部由 Claude 在工作流开始时写入：任务总目标、threadId、任务书原文。

**Claude 读取规则（防止双倍上下文开销）——只在以下三种情况读日志文件：**

1. 上下文被压缩后需要找回历史汇报或 threadId。
2. 新会话恢复中断的工作流。
3. 需要核对某轮的完整细节（精简汇报不够用时）。

正常轮次中，汇报已通过工具结果进入上下文，**不得**再读一遍文件。

**状态清单（ACTIVE.md）**：`<项目根>/.codex-agent/ACTIVE.md`，每行一个工作流：

```
- <slug> | 状态: active/blocked/done | threadId: xxx | 轮次: N | 下一步: <一句话>
```

由 Claude 维护：每轮汇报验收后、发起下一轮**之前**更新对应行（一次约百 token 的小编辑）。工作流完结改为 done。

**轻量簿记（2026-07-16 提速修订）**：预计 ≤2 轮的工作流免文件头预写和逐轮 ACTIVE.md 维护——结束时一次性写简化日志（任务一句话 + 最终汇报 + threadId/session id）+ ACTIVE.md 直接记一行 done；中途扩到第 3 轮起转全量簿记。全量簿记保留给多轮/长期工作流，恢复保障不受影响（≤2 轮的工作流丢了重发即可，重发成本低于逐轮簿记的累计成本）。

**恢复流程（上下文压缩 / /clear 重置 / 会话切换通用）：**

1. 锚点：skill 内容和对话历史都可能被压缩掉，CLAUDE.md 是每个上下文窗口都会重新注入的唯一持久锚点——触发规则中固定一行"开始代码工作前，若项目根存在 `.codex-agent/ACTIVE.md`，先读取并恢复未完结工作流"。没有这个锚点，落盘的一切都不会被发现。
2. 读 ACTIVE.md → 定位未完结工作流 → 读对应日志文件的文件头与最后一轮汇报。
3. 先尝试 `codex-reply` + 记录的 threadId（MCP server 未重启时 thread 仍存活，恢复零成本）；失败则按第 6 节冷启动。
4. 轮次边界纪律：状态更新先于下一轮下发，任意时刻被压缩或重置，最多丢失当前进行中的一轮。

**多工作流切换**：并行多个工作流时各自独立日志文件 + ACTIVE.md 各占一行；切回某工作流前先读其状态行，不依赖对话记忆。

**多终端 / 多项目并发：**

- 多项目：skill 全局唯一（`~/.claude/skills/`），状态严格项目本地化（`.codex-agent/` 在各项目根），cwd 每次显式传——项目间零共享、互不干扰。
- 多终端同项目：每个 Claude Code 会话有自己的 codex mcp-server 进程，**thread 不跨终端存活**。因此工作流归属创建它的会话；其他终端对不属于自己的 active 工作流发 `codex-reply` 必然失败——接管必须经用户确认，并走冷启动流程。
- ACTIVE.md 并发安全：更新一律用行级 Edit（精确替换本工作流那一行），禁止整文件重写（初次创建除外），避免并发会话互相覆盖。
- slug 唯一性：开新工作流前查 ACTIVE.md，slug 已被 active 状态占用则换名。
- 范围隔离：同项目多会话并行委托时，各任务书「涉及路径」不得重叠；git 检查点发现他人未提交改动时，不得 stash 他人改动，改为提醒用户处理。

**清理策略**：工作流验收完成后，日志文件保留归档；是否删除由用户决定，Claude 不主动清理；ACTIVE.md 中 done 条目在下次更新时移除。

**收益边界（评估结论）：** 该机制的价值在持久化（抗压缩、跨会话恢复、审计复盘）和新 thread 冷启动提速；对同一 thread 内的常规轮次没有收益，因此上述规则明确禁止轮内重复读写。

## 9. 预期收益评估与验收指标

以下为推理估计（非实测），基准场景：中等规模任务（探索 + 跨文件实现 + 测试修错，约 3 轮）。

### 9.1 Claude 上下文 token 节省 —— 核心收益，估计 85–95%

| 阶段 | Claude 自己做 | 委托方案 |
|---|---|---|
| 探索 | 读 10–30 个文件，约 30k–100k token | 精简汇报约 300–800 token |
| 实现 | 反复读写文件、看 diff，约 20k–60k | 任务书约 500–1k + 抽查约 1–3k |
| 测试循环 | 测试输出约 5k–20k | 汇报结论约 300–500 |
| **合计** | **约 60k–180k** | **约 5k–15k** |

直接后果：上下文压缩触发次数大幅下降，单会话可承载任务量成倍增加。

### 9.2 延迟改善 —— 分机制差异大

| 机制 | 估计幅度 |
|---|---|
| 任务书注入已知上下文（跳过探索） | T2 首轮省 30–60% |
| `approval-policy: never` | 消除全部审批等待 |
| T1 低推理档 | 探索类单轮省约 30–50% |
| threadId 复用 | 第 2 轮起省 50–80% |
| 落盘机制 | 常规轮次 0（收益在韧性，按事件计） |

首轮存在物理下限：实现工作本身的耗时不会因委托而消失，方案消除的是浪费部分（重复探索、审批、过深推理）。

### 9.3 成本与盈亏平衡

- 每轮固定开销：任务书 + 等待 + 解析汇报 ≈ 1–2 分钟、约 1–2k token。
- 盈亏平衡点：Claude 直做会消耗 >10k 上下文 token 的任务净赚；5k 以下打平；T0 级别净亏（故排除）。
- 系统总 token（Claude + codex 合计）估计比单 agent 高 10–30%：本质是用 codex 配额换 Claude 配额与上下文窗口空间。

### 9.4 验收指标（实现后 A/B 实测）

同一真实任务，委托 vs Claude 直做各一次，对比 `/cost` token 消耗、总耗时、轮数：

| 指标 | 达标线 |
|---|---|
| Claude 侧 token 降幅 | ≥80% |
| 总耗时 | ≤ 直做的 1.3 倍 |
| 一次任务书达成率（无需修正轮） | ≥70% |

任一不达标 → 回头调协议（优先检查任务书模板的上下文注入是否充分）。

### 9.5 A/B 实测结果（2026-07-16，任务：生成项目顶层 README）

| 指标 | A 臂（直做） | B 臂（委托） | 达标线 | 判定 |
|---|---|---|---|---|
| Claude 侧 token | 50,024 | 57,565（+15%） | 降幅 ≥80% | ❌ |
| 耗时 | 4 分 13 秒 | 10 分 16 秒（2.44×） | ≤1.3× | ❌ |
| 一次任务书达成率 | — | 2 轮均一次达成，0 修正轮 | ≥70% | ✅ |
| 产出质量 | 事实密度高 | 结构/诚实度/指引更优，胜出 | — | B 胜 |

失败原因与已落实的协议修订：

1. **协议固定开销在中等体量任务上吃掉全部收益**（读 SKILL.md、任务书、汇报解析、日志维护 ≈ 数万 token）。修订：路由表加实测边界——委托仅用于直做预计 >约 60k token、主会话上下文紧张、或需长时间自治的任务；原 10k 盈亏平衡点估计过于乐观，作废。
2. **sandbox 是 thread 级配置**：read-only 的 T1 thread 无法续接 workspace-write 的 T2，B 臂被迫冷启动第二个 thread（结论经日志传递），额外增加延迟。修订：探索后必实现的任务直接开 workspace-write thread 一轮完成"探索+实现"；仅当探索结论需 Claude 决策后才实现时拆两个 thread。
3. **codex 看不到自己的 threadId**：日志轮次标题要求自标 threadId 不可行。修订：改由指挥方验收时补记。

结论：该结构的真实价值在**保护主会话上下文**（把探索/实现的大量 token 留在 codex 侧）与**长任务自治**，不在中小任务的绝对 token/时间节省。路由阈值已相应上调。

### 9.6 B2 复测（修订协议，同任务重跑，2026-07-16）

### 9.14 v3.1：使用期加固（用户实战修订，2026-07-18 归档）

1. **brief 非空校验**（exit 4）：路径错误/空任务书在发射前拒绝，不再烧掉一轮 codex。

5. **用户汇报义务缺失**（使用期发现的协议盲区）：协议为省 token 优化了机器通路（汇报进文件、日志落盘、轻量簿记），却未规定大脑对用户的交付义务——实战表现为对话里只剩"已完成+文件路径"，结论本体全进文件、用户被迫自己翻。修订：SKILL 第 6 步与 protocol §7.7 新增硬性规则——落盘不豁免当面汇报；交付物摘要、探索/审校类的结论本体、验收结果必须进对话；禁止用"详见 xxx.md"替代实质。token 节省的对象是过程噪音，永远不是用户要的结果。
